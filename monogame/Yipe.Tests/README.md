# Gameplay and input checks

Run from the repository root:

```sh
dotnet run --project monogame/Yipe.Tests -c Release
```

The executable checks core rules, animation/input state and isolated save files
without opening a game window. Failures terminate with a nonzero exit code.
Graphics verification is documented in [Yipe.GraphicsChecks](../Yipe.GraphicsChecks/README.md).

Footstep asset checks verify the fifteen recorded WAVs copied into the build:
16-bit mono compatibility, contact duration, clean boundaries, mixing headroom,
distinct variants and matching CC0 source credits/hashes. [Sources and credits](../Yipe.Desktop/Content/Audio/Footsteps/README.md).

## Original random generator

`Yipe.Core.MsvcRandom` implements the Visual C++ generator used by the supplied
game. `Next()` returns the original 15-bit value; `State` exposes its complete
32-bit state without advancing it. The constructor accepts either an initial
seed or a stored state. Its default seed is 1. Arithmetic wraps explicitly with
`unchecked`, including when the project enables overflow checking.

The test reference is generated by compiling [random_reference.cpp](random_reference.cpp)
with the existing [C++ implementation](../../src/random.cpp). It emits 1,024
draws for each of eight seeds: 0, 1, 2, `0x7fffffff`, `0x80000000`, `0xffffffff`,
`0xdeadbeef`, and the recovered generated-map regression seed 2566201570.
Each record contains decimal `seed,step,value,state`, terminated by LF.

```sh
mkdir -p build/monogame-reference
c++ -std=c++20 -I include monogame/Yipe.Tests/random_reference.cpp src/random.cpp -o build/monogame-reference/random-reference
build/monogame-reference/random-reference > build/monogame-reference/random-reference.csv
shasum -a 256 build/monogame-reference/random-reference.csv
```

Expected SHA-256 for the 8,192 LF-terminated records:

```text
d7581cd4181ee25851126078623cb2b8cee4283505cd00255295a7b4fd1e7ff8
```

The C# test produces the same records from its own implementation and compares
the digest. This checks every output and post-draw state, including each final
state. Separate checks cover the original default sequence, preservation of all
seed bits, and continuation after restoring state. On a toolchain that translates
stdout to CRLF, normalize line endings to LF before comparing the reference file.
Do not replace the expected digest with C# output to resolve a failure.

To verify wrapping under checked compilation:

```sh
dotnet build monogame/Yipe.slnx -c Release --no-restore -p:CheckForOverflowUnderflow=true
dotnet run --project monogame/Yipe.Tests -c Release --no-build
```

The session owns the generator used by the character and command rules below.
Rendering and ordinary movement through the town do not consume it.

## Character rules and reference

[Player](../Yipe.Core/Player.cs) ports all state and methods from
[player.hpp](../../include/yipe/player.hpp) and [player.cpp](../../src/player.cpp).
It owns fixed-size arrays independently for each character. Its creation presets
are Warrior/Combat, Rogue/Quickness and Wizard/Magic; random creation starts from
a preset and calls `RerollRandomCharacter` on the session's RNG. Rerolls continue
that stream and leave name, difficulty, equipment and unrelated state intact.
`CombatStyle` is the saved level-up bias, separate from `Specialty`.

`TryLevelUp` grants at most one level per call, using the original XP thresholds
and RNG order. It increases current and maximum HP/SP together without filling
their existing deficits; AP is unchanged. New characters inherit the C++
[D8 adaptation](../../docs/DECISIONS.md): stat cap mode 2 (50). Modes 0/1 retain
30/40, and other mode values use the reference's fallback of 30.

`UseInventoryItem` returns consumption, rolled amount, sound ID and the original
message. Rolled healing can exceed the actual change after capping. Sound IDs
remain data for the later audio adapter. Callers supply map/combat context;
the defaults match C++, even if the character stores another current map.
Surface potions set `PendingRelocation` to 1; `WorldLocation.ApplyPendingRelocation`
applies the coordinate change; `GameSession.UseInventoryItem` now loads the
destination and places the player before returning. The core can address all 30 stored slots, but the inventory UI must expose
only the 13 carried slots. Unknown items in later metadata slots are retained,
including the original message quirk saying that they were removed.

`InventoryValues` preserves unsigned storage while rescue counting interprets
each entry as a signed 16-bit value. Return regions and Hell gatekeeper outcomes
remain signed. Defeat counters wrap at 32 bits, and accumulated repellent time
wraps at 16 bits, explicitly even under checked compilation.

[player_reference.cpp](player_reference.cpp) calls the existing C++ implementation;
it contains test inputs and output formatting, not copies of gameplay formulas.
[PlayerChecks.cs](PlayerChecks.cs) runs the corresponding C# cases and checks
13 independently generated section digests. The **11,322 records** cover:

| Cases | Records |
| --- | ---: |
| All three starting presets | 3 |
| Consecutive random rerolls over eight seeds | 512 |
| Healing/damage and negative health | 25 |
| XP thresholds, including invalid and capped levels | 105 |
| Levels 1–100, three difficulties, XP boundaries and RNG states | 7,200 |
| Level stat caps and stat potions below/at/above each cap | 90 |
| All consumables and invalid items across carried/metadata slots and contexts | 3,120 |
| Surface-potion restriction precedence | 16 |
| Repeated repellent use | 10 |

Except for the threshold-only rows, each row includes all 65 scalar fields,
all seven arrays and the computed stat cap. Operation results and relevant RNG
states precede that snapshot. Rows use invariant decimal numbers, 0/1 booleans,
numeric enum values and LF endings. Scalar and array order follows the oracle's
`state` function. This is a diagnostic fixture format, not a game save format.

## Maps and world movement reference

[MapCatalog](../Yipe.Core/MapCatalog.cs) reads the existing v5 JSON catalog without
changing its column-major layout. It validates dimensions, array sizes, event
coordinates, IDs, numeric widths and required fields. `CreateMap(id)` returns a
fresh mutable [Map](../Yipe.Core/Map.cs), or null for an unavailable static ID.
The 112 templates include all original static events. The separate chest table
also retains the two slots for generated map `0x78`. P1 completion adds generated
construction through `LoadMap`, verified separately below. Map copies own their tiles and event arrays.

`Map.Move` accepts one of eight adjacent directions from an in-bounds origin.
It returns the original action code, destination and whether position changed;
it does not execute actions or consume RNG. It preserves equipment gates,
overlay substitution and depth-event precedence. Diagonals test only the target,
with no extra blocked-neighbor rule. Zero-length moves, jumps and out-of-bounds
origins are rejected at the C# API boundary. Doors, linked tiles, chest removal
and overlay restoration mutate only the current instance. D7's saved-platform
support is retained; advancing platforms and visibility remain later work.

[WorldLocation](../Yipe.Core/WorldLocation.cs) preserves region wrapping, edge
and depth action order, alternate-map offsets, return-to-surface behavior and
all four queued relocations. Surface return retains the current tile until the
caller loads the destination and uses `Map.SurfaceReturnPosition()` to find the
last entrance in column-major order. Character/map synchronization and supported commands now belong to `GameSession`.
The desktop uses its town adapter to render the same map instance and explicitly
disables map changes at the preview boundary.

[map_reference.cpp](map_reference.cpp) links directly to the C++ map implementation
and its generated catalog, independently of the C# JSON parser. Nine section
digests compare **311,728 records**:

## Session commands and entry reference

[GameSession](../Yipe.Core/GameSession.cs) owns Player, WorldLocation, MsvcRandom,
the current map and a read-only view of remembered tile changes. It takes a copy
of an input location; the caller transfers its mutable Player to the session.
`SessionMoveResult` reports the original action code, final position, whether the
position/map changed, map-transition status, restoration and fire damage.
`Disabled` is the preview boundary; `Unavailable` covers destinations without a
loader. Disabled and unavailable transitions do not change the live session or RNG.
Generated maps now load normally through the session RNG.

Opening first loads the saved map, then applies any queued relocation; otherwise
it synchronizes
character/location, initializes the map, applies remembered tiles and restores D7
platform support at the saved position. `Map.InitializeActions` filters opened or
wall-covered chests, applies the original strength/gatekeeper/stamp conditions,
clears an entry trap and rearms healing water except on map zero. Entry changes
are transient; remembered door/switch tiles take precedence and survive reloads.
The signed comparisons for stored gatekeeper/stamp fields are retained.

Movement executes doors and linked switches, static edge/depth loading and surface
return recording. Blocked restoration/fire tiles and linked travel execute their
core actions. A waiting Hell gatekeeper still requires its later choice/encounter
interaction; it cannot be bypassed. `UseInventoryItem` supplies actual session
map context and applies queued relocation after item use. Surface return selects
the original template's last entrance before entry actions and remembered edits.
Unavailable queued destinations throw without clearing or applying the relocation;
item consumption occurs first, as in the reference application. The full-save
codec now rejects inconsistent saved destinations before live restoration.

The remainder of arrival handling is still unported: hint, location message,
princess, encounter and chest, in that order; a resolved or collocated encounter
suppresses chest opening. Visibility, transient encounter resets, timed events
and finale completion are also later P2/P3 work. `OriginalCode` and current map
records supply their handoff data, not an automatic reward or combat resolution.
No generic command/event framework or separate renderer state model was added.

[session_reference.cpp](session_reference.cpp) calls the C++ entry, movement,
door/switch, restoration, fire and teleport primitives. Its small action sequence
mirrors the corresponding branches of [app/main.cpp](../../app/main.cpp); it does
not run the SDL application or reproduce its complete event pipeline.
[SessionChecks](SessionChecks.cs) executes matching cases through the C# session:

| Section | Coverage | Records |

| Action | Real map doors, switches, locks, restoration, fire and linked travel; no/all equipment, three successive visits | 2,058 |
| Restore | Difficulty/use limits and restored HP/SP/AP | 45 |
| Fire | Boundary seeds, difficulty, level and health, including two draws and lethal-damage floor | 144 |

## Full-state save checks

P1.5 adds [GameSaveChecks](GameSaveChecks.cs) and the native
[version 1 compatibility fixture](Fixtures/full-save-v1.y3m). The binary format,
validation bounds, snapshot and replacement rules are specified in
[SAVE_FORMAT.md](../SAVE_FORMAT.md). This is a distinct MonoGame format, not a
reader for the C++ or original game formats.

At the P1 baseline, the normal runner performed **478 checks** on the verified macOS host. The
full-save section adds **141** checks to the preceding 226. It covers all 65
Player scalar properties and seven arrays through independent test reflection,
Unicode/raw signed metadata, world coordinates and alternate maps, persistent
changes, defeated placement IDs, ownership isolation and exact RNG continuation.
The codec itself does not use reflection. A fixed fixture detects accidental
version 1 layout changes; do not regenerate it to hide compatibility failures.

Further cases reject every truncated prefix, wrong formats/versions, corrupted
hashes and payloads, oversized input, invalid UTF-8, flags, coordinates, bounded
counts, duplicate edits/defeats and unavailable maps. Some malformed payloads
have valid recomputed hashes to exercise structural validation separately from
integrity checking. Reload tests retain entry, queued relocation and D7 behavior.

Storage tests use unique temporary directories, cover synchronous snapshot capture
before asynchronous writes, replacement, actual permission/replacement failures,
cleanup and concurrent writers. The permission-specific pair runs on Unix;
Windows skips those two assertions and still needs platform verification. No
user save paths are used. Preview migration/import coverage is described below.

The normal suite starts separate writer and reader processes. The reader compares
the entire reconstructed snapshot and continues item use/RNG draws against a fresh
expected session. The additional P1 completion suite below verifies generated-map
regeneration and C++ import/reopen parity.

For an explicit diagnostic restart, from the repository root after building:

```sh
mkdir -p build/monogame-reference
dotnet run --project monogame/Yipe.Tests -c Release --no-build -- --write-save-fixture build/monogame-reference/restart.y3m
dotnet run --project monogame/Yipe.Tests -c Release --no-build -- --read-save-fixture build/monogame-reference/restart.y3m
```

The writer overwrites its specified `.y3m` output; the reader changes no files.
These modes return before the ordinary test suite. The fixture exercises persisted
state, not earned campaign progress. The graphics runner separately verifies full
pause-menu save/load, renderer replacement and failures without live-state changes.
